Instructions for Claude Code when working in this repository. Read this file fully at the start of every session.

## Project

A web game for the Bio-Streams (EU) science competition. The topic is **childhood obesity**. The player cares for an avatar who is a school student and tries to raise its health (1 to 5) through **sport, sleep and food** (food is secondary only in the order of development).
The author is a 9th-grade student competing in the national phase. Goal: win and present in Athens. The game must be scientifically sound, and everything in this repository is **public and free for anyone to use**.

## How to work with the user

- Always answer and think in **English**. Keep files in the language they already have (the game text is Portuguese and English).
- Be professional and clear. The user is a student: explain what you did in plain language and give exact steps (menus, commands) whenever the user has to do something.
- **Always read the current code before suggesting or making changes to it.** If instructions to modify code are needed and the code is not in front of you, ask the user for it first.
- Work in small steps. After each step say what changed, how to run it, and what to check.
- Do not invent game rules. If a rule is not written in this file or the concept document, use a **placeholder value in `data/config.json`**, mark it with `"placeholder": true` in a comment field, and list it in your reply.
- Do not save secrets, passwords or personal data in the repository.

## Technical decisions (fixed)

- **Godot 4.6.3**, **GDScript**, **Compatibility renderer** (`gl_compatibility`). Do not use Forward+ or Mobile (the dev Mac is Intel with weak graphics, and Compatibility is the only one for web). Do not upgrade Godot.
- **Platform: web page for all devices** (computer, Android, iOS in the browser). Native apps are optional and only if there is time. **Test first on the Mac.**
- Portrait base resolution **720 x 1280**. On wide screens the game stays in a **centred column**. Use Control nodes with anchors and containers; stretch mode `canvas_items`, aspect `keep`.
- **No server, no accounts, no notifications, no daily limit.** The first version saves locally on the device. Keep **time and saving in separate scripts** so a server can replace them later without changing the rest.
- Web build is exported to the `docs/` folder and published with **GitHub Pages**. Keep documentation in `documentation/`, never in `docs/`.
- Data-driven: foods, activities and all tunable numbers live in `data/` (JSON), not in code.
- Texts go through Godot translations (`translations/strings.csv`, columns `keys,en,pt`) with **pt** and **en**. Scenes, `scripts/ui/` and `data/activities.json` hold keys, never plain text; text written from a script uses `tr()` and is written again on `NOTIFICATION_TRANSLATION_CHANGED`. Numbers with decimals go through `Settings.number()` (decimal comma in Portuguese). After changing the CSV run `Godot --headless --path . --import`. The debug panel, the CSV log and test output stay in English. Language is chosen in settings and on the creation screen (Milestone 11: first start follows the browser's language; decisions 14 and 15). Wording is scientifically correct and not simplified for small children.
- **Avatar art (6 Nov 2026):** four sprite sheets made by the team with an AI image tool (CC BY 4.0, README), one per age group and sex, with 5 bodies (obese, overweight, healthy, thin, muscular) and 5 faces (happy, neutral, sad, tired, asleep). The originals are in `assets/art/avatar/source/` (with a `.gdignore`, so they are not in the game), and the team's AI-upscaled grids (7 Nov 2026, about 3.6 times, white background) in `assets/art/avatar/source/upscaled/`. `tools/cut_avatar_sheets.py` cuts the originals into even 5 x 5 grids of the avatar's size (330 x 450, 1.5 times the egg; user, 6 Nov 2026), uses those grids to turn the upscaled sheets' white background back into transparency, and saves one picture per body and face at twice the avatar's size (660 x 900, sharp on dense phone screens and far below the 4096-pixel texture limit of many phones) as `assets/art/avatar/<sheet>/<body>_<face>.png`, each scaled to the median height of its sheet and moved so its feet are in the middle and on the ground (the team's figures do not stand in the same place or have the same height, so the avatar moved and its head jumped when its picture changed; user, 7 Nov 2026), imported as lossy WebP (quality 0.85) with mipmaps; the avatar loads the current picture when its states change, never inside `_draw()` (a texture loaded while drawing is drawn white); the drawing does not move like the egg did (no hop, squash or breathing; user, 6 Nov 2026), it only closes its eyes to sleep; `data/avatar_art.json` lists the sheets, the column and row order and where the mouth is. The egg is still drawn when there is no sheet (before creation, in the editor) and on the football field. Other art is placeholder shapes, including the places behind the activities (`scripts/ui/scenery.gd`). Plasticine art is optional, later.

## Game rules (confirmed)

**Measures**
- Health: 1 to 5, **calculated from the measures**, not fixed. Health = 1 + 4 × the **power mean** of Physical, Happiness and Sleep with **p = 0.5** and equal weights (v1 Step 11; built in Milestone 10 Task 8, `scripts/health/health_model.gd`). The target health follows the measures every step; the displayed health (the bar) moves `health.alpha_bar` (0.37) of the way to it once per avatar day, when a sleep ends (decision 1). The formula gives the **target health**. The **displayed health** (the health bar) starts at the target and then moves part of the way toward it once per avatar day, when a sleep ends (`health.alpha_bar`, 0.37, placeholder). During the day health does not change. The **health level** is health rounded to a whole number (1 to 5).
- Physical: 0 to 1 (0.44 on Normal in v1). v1 Step 8: Physical = (0.5·√w + 0.3·√fitness + 0.2·√strength)² × (0.4 + 0.6·Q) × (1 − 0.5·U) × (1 − 0.3·O), with w the weight score from the WHO BMI-for-age z, Q diet quality, U energy deficit penalty, O overreaching. Built in Milestone 10 Task 8; worked out every step. Its values are kept separately in `GameState`: **fitness** and **muscle** (0 to 1, slow body states that change once per avatar day, see "Health calculation (working plan)"), the **weight z-score**, and **calories spent** (total kcal spent by exercise, never reset; a record only). Fitness takes the place of the planned "endurance".
- Happiness (called Mental before Milestone 10): 0 to 1, 0.50 on Normal. It moves toward a baseline (from Physical, Sleep, diet quality, fun, deficit, screen excess, overreaching) with a 12-avatar-hour time constant and jumps with events; **`mood.speed` (0.5, placeholder; user, 7 Nov 2026) makes all of it 2 times slower, rising and falling alike: the time constant is 12 / 0.5 = 24 h and every event (per hour or at once) is x 0.5**, so v1's end results stay and only the pace changes (a slower time constant alone would make every hourly event stronger: rate x time constant) (meals, exercise, football, screens, hunger, waking); k does not apply (v1 Step 10). It replaces the Milestone 4 mood and habit-change cost model.
- Sleep: 0 to 1, 0.50 on Normal. v1 Step 9: Sleep = (1 − min(1, debt ÷ 8)) × (1 − min(0.3, 0.1 × oversleep)); the sleep debt factor d slows training gains, raises appetite and lowers exercise capacity. Sleep never changes the metabolic rate.
- The starting states come from the chosen difficulty (`health.difficulties` in `data/config.json`); the starting measures and health are calculated from them. Before the player chooses, the Normal values are used.
- XP: unlimited (v1 Step 12, built in Milestone 10 Task 8, `scripts/health/progress.gd`; values in the config group `progress`, placeholders). Every change of the displayed health gives or takes `per_health_point` (100) XP per point. Every avatar hour while the displayed health is at least `high_health_min` (4.5) gives `gain_per_avatar_hour` (10) x (1 + hours at that level without a break / `bonus_hours` (48)), at most x `max_multiplier` (3). There is no hourly XP loss at low health. XP never goes below 0. The level is XP ÷ `xp.per_level` (rounded down), so losing XP can lower the level; a new level shows "Level up!" in the speech bubble for a few seconds. **Every XP change is shown under the XP bar** (user, 7 Nov 2026): `GameState.xp_changed` sends the real change; the main screen adds the changes up and shows them as a whole number ("+37 XP" in green, "−20 XP" in red) that rises and fades, at most one every 1.5 real seconds; nothing is shown while a save loads. The XP rules did not change.
- Sport, sleep and food drive progression.
- **Player choices:** age group (child or teenager), sex (male or female) and difficulty. The age sets the recommended sleep range (child 9 to 12 h, teenager 8 to 10 h; placeholder) and the sex sets the WHO BMI-for-age tables. The player chooses them, with the avatar's name, on the **avatar creation screen**, which opens when there is no save; they are saved in `GameState`. Nothing is saved before Start is pressed. On phones and tablets in a browser the name field says "Tap to type a name" and a tap opens the browser's own text box (`window.prompt`), because Godot's web text field does not reliably receive on-screen keyboards. This pop-up box is confirmed on a real Android phone; the user chose to keep it (30 Oct 2026, `scripts/ui/creation.gd`).
- **Deleting a save on the web** (`SaveGame.delete_save()`, Milestone 11): the browser can give back the deleted file after a reload, so the last save number is written to localStorage and copies that are not newer are ignored. New saves count on from it.
- **Old saves do not load.** The save has a version number (`SaveGame.SAVE_VERSION`); a save of another version is ignored, the creation screen opens and the player starts a new avatar (the old save is replaced when the new avatar is saved). Version 2 = Milestone 10 (v1 health system): saves from Milestone 4 or earlier (version 1) do not load (decision 6, user, 25 Oct 2026). A save without the creation choices is ignored too. Every GameState value is saved, except the two per-step values `energy_spent_step` and `beyond_capacity_minutes_step`, which are worked out again every step; the Clock, the running activity, the action log and Simulation's pending minutes are saved too (`tests/save_test.gd`).
- **Difficulty and starting values (v1, placeholders; Physical, Happiness, Sleep → health):** Easy (0.71, 0.75, 0.75) → 3.94; Normal (0.44, 0.50, 0.50) → 2.91; Hard (0.14, 0.30, 0.30) → 1.95, obesity, habits cheap to change; Very hard (0.03, 0.15, 0.10) → 1.35, severe obesity, very bad habits (starting happiness 0.15, not the concept's 0.05: open decision 1). Each difficulty also sets z, fitness, strength, diet quality Q, craving C and sleep debt (table in the v1 document). Starting health comes from these measures.
- **Health calculation:** built in Milestone 10 following Health Calculation Architecture v1; see the section "Health calculation (v1, built in Milestone 10)" below. All numbers are placeholders in `data/config.json` (status and owner on each).
- **Exercise limits (v1 Step 6).** Daily capacity = (60 + 90 × fitness) × (1 − 0.3 × d) minutes; minutes beyond it give no benefit, cost a little happiness and build an overreaching load O. Strength started before 60% recovery (24 h time constant), or less than 36 avatar hours after the start of the previous strength session (Milestone 10.5, team review; `train.strength_min_gap_h`, placeholder), counts as too soon. "Tired" (tiredness) comes from sleep debt and hours awake, not from exercise.

**Time**
- Day = **20 real minutes** = 14 avatar hours (1 real minute = 42 avatar minutes; v1; `time.day_avatar_minutes_per_real_minute` in config, built in Milestone 10 Task 2).
- Night = 2 real hours = 10 avatar hours of sleep (1 real minute = 5 avatar minutes). Sleeping less is proportional (8 h of sleep = 96 real minutes).
- **Sleep-to-day conversion (confirmed).** The baseline is 10 hours of sleep and a 14-hour day (24 hours in total). Hours slept below 10 are **added to the next day** and hours slept above 10 are **taken from it**: `day_hours = 14 + (10 - sleep_hours)`. Example: 5 hours of sleep give a 19-hour day, and 12 hours of sleep give a 12-hour day. The day's real length uses the same scale: `day_real_minutes = day_hours * 60 / 42` (19 h is about 27.1 real minutes, 14 h is 20 real minutes). The 10 h only sets the scale; recommended sleep comes from the age (child target 10.5 h, teenager 9 h). The first day is 14 hours.
- Implement this as one small, well-tested conversion function in `Clock` (avatar hours to real seconds, and back), with the numbers read from `Config`. Put the maximum sleep on the slider in config (placeholder, for example 12 hours).
- A **24-hour clock** in the interface (in the top-right column, under the XP level box, above the pause button) shows the avatar's time of day. Placeholder: the first day starts at 07:00. With this conversion bedtime stays at the same clock time and the wake-up time moves with the hours slept.
- While the avatar plays football avatar time runs 5 times slower (decision 47).
- Game time only advances while the game is open. Closing the tab pauses time.
- A pause button stops the day. The night starts when the day ends, but sleep is **not automatic**: the avatar gets tired, shows a recommendation to sleep, and the player decides. When sleep ends, the game pauses and a **wake button** starts a new day.
- Sleep is optional and variable (a slider chooses the hours). Not sleeping lowers health significantly.
- **When the avatar can sleep (v1 Step 9).** Only when its sleep debt is at least 1 h or it has been awake at least 6 avatar hours; otherwise it says it is not sleepy. It wakes after the chosen hours, never later than the maximum plus min(debt, 2 h). Within that rule the sleep button works at any moment of the day, not only at bedtime. Built in Milestone 10 Task 2 (`Clock.is_sleepy()`, `Clock.max_sleep_hours()`; until Task 6 the debt is the Milestone 4 `sleep_debt`); pressing Sleep when not sleepy shows "I'm not sleepy." and the slider stops at the longest sleep allowed. A nap is simply a short sleep and follows the same rule: when any sleep ends, a new day starts whose length is `14 + (10 - hours slept)`, so one sleep plus the awake period after it always adds up to 24 hours.
- **Ignoring the sleep recommendation (confirmed).** If the awake period runs out and the player has not slept, it counts as **0 hours slept**: a new 24-hour day starts at once, the avatar stays tired and the sleep measure keeps falling. The recommendation stays visible, and the player can still sleep at any time.

**Food and mood** (built in Milestone 10; v1 Steps 4, 5, 7 and 10)
- The player chooses what the avatar eats: a healthy meal or a fast-food meal (0.5 avatar hours each), when it says "I'm hungry!" or at any time while awake; a hungry avatar can also skip a meal. Menus and tastes are decided later (decision 3: two meals only).
- Fast food makes the avatar fatter (more kcal, fills less) and lowers diet quality, which lowers Physical; it supports happiness while the craving is high. A healthy meal with a high craving makes the avatar a little sadder.
- A gradual fast-food-to-healthy change keeps happiness higher than an abrupt one, and Physical recovers. Fast food alone does not lead to failure (v1 open decision 2); very low happiness for 12 avatar hours is failure.

**Failure**
- **Team decision (22 Oct 2026): there is no death, only failure.** v1 Step 12 (to tune): failure when the **target health** (not the slow bar; decision 10, Milestone 10.5) is below 1.3 for 24 avatar hours, happiness below 0.10 for 12 avatar hours, or an irreversible disease (disease framework only; which diseases is not decided). **The failure screen (Milestone 17, user, 7 Nov 2026, `MILESTONE_17.md`):** failure is final and saved (`GameState.failed_cause`, `failed_day`); time stops (`Clock.halted`) and an activity ends (a sleep only stops); a screen over everything shows the avatar, a short phrase per cause ("Ana lost too much weight.", not the scientific cause), Details, drawn rather than written (user: "more graphical and user friendly"): the exact cause, tiles for the avatar's life and body (the level boxes' style), bars for its last measures, and a gauge per habit over the last `failure_screen.summary_days` with the recommended zone in green and a marker for the avatar (`scripts/ui/habit_gauge.gd`; meals as a green and orange bar), and a short verdict where a value needs one (BMI-for-age "too thin", "too heavy"...; each measure "too low", "could be better" or "good"): facts, not advice and Start a new avatar (concept: after failure the player restarts with a new avatar). While a failure timer runs, the health bar warns (red, "Health: danger"). Do not build any death system. Built in Milestone 10 Task 8 (failure timers in `GameState`; the disease part is only a risk index and hidden damage in the debug panel, decision 9).
- **Danger state of severe thinness (Milestone 10.5, team review; placeholders in the `fail` group).** Below BMI-for-age z −3 (WHO severe thinness) the avatar is in a reversible danger state: it looks thin and ill and the health bar warns. It ends only when z is back at −3 or above (decision 11). It is failure when it lasts 72 avatar hours, or at once when z reaches −4. The risk index has a thinness term that mirrors the obesity term.

## Health calculation (v1, built in Milestone 10)

Source: **Health Calculation Architecture v1** (`documentation/health_calculation_architecture_v1.md`, a copy of the Google Doc; "Bases fundamental" has priority) and the user's decisions in `MILESTONE_10.md`. The plan of the replacement is `documentation/milestone10_plan.md`; the scenario results for the team are `documentation/milestone10_calibration.md`. The older plan ("Architecture Decisions: Health System", Milestone 4: k = 5, mood and habit-change cost, habit scores, p 0.2) is replaced; `MILESTONE_4.md` and `documentation/milestone4_audit.md` are kept only as a record.

**How it is built.**
- **Every number is in `data/config.json`** (groups `units`, `activity_slider`, `who`, `body`, `energy`, `appetite`, `meals`, `deficit`, `train`, `minigame`, `diet`, `sleep`, `mood`, `health`, `fail`, `risk`, `progress`, `avatar_states`, `log`), each value written as `{"value": ..., "status": "placeholder" | "team decision" | "from source", "owner": "Pessoa 1 to 4" or "team"}`; `Config.get_value()` returns the value and `Config.is_placeholder()` is true for status "placeholder". Foods are in `data/foods.json`, the METy of each activity in `data/activities.json`, and the WHO 2007 tables in `data/who_bmi_for_age.json` and `data/who_height_for_age.json`. No number is left in `scripts/health/` or the health autoloads (`tests/config_test.gd` checks it). In debug builds **F6 reloads the config** while the game runs.
- **All state is in `GameState`**; each v1 module is a script in `scripts/health/` with static functions that read Config and update only the state it owns: `who_tables.gd`, `body_size.gd`, `energy.gd`, `hunger.gd`, `training.gd`, `sleep_model.gd`, `diet.gd`, `happiness.gd`, `health_model.gd`, `risk.gd`, `progress.gd`, `avatar_states.gd`, and the helper `hour_window.gd` (sliding 24-hour sums). They use the autoloads, so tests load them at run time with `load()`, not `preload`.
- **`Simulation`** runs the update loop in fixed steps of 5 avatar minutes in the v1 order: clock (hours awake) → energy spent → hunger → body age, height and z → energy deficit U → training → tiredness → Physical → happiness → health, failure timers, risk and XP. Events run when they happen: a meal (when it ends), the start of an activity, and the new avatar day after any sleep or the 0-hour rule (sleep debt, Sleep, night quality, daily capacity, screen minutes, the health bar step). Results do not depend on the frame rate. While a save loads, `Simulation.loading` blocks repeated events.
- **Player choices:** age group child (reference age 10) or teenager (14), and sex, set the WHO rows, the BMR equation and the sleep range (child 9 to 12 h, target 10.5; teenager 8 to 10 h, target 9). The body grows only inside its age group (decision 8). Starting values per difficulty: see "Difficulty and starting values" above; starting Physical, Sleep and health are calculated, never typed in.

**Food as an activity (built in Milestone 10 Task 3).** The Eat button opens Healthy meal and Fast-food meal (0.5 avatar hours each, `data/activities.json`; food values in `data/foods.json`) and, when the avatar is hungry, Skip meal. `scripts/health/energy.gd` gives the Schofield BMR, the reference appetite (BMR at the WHO healthy weight x `energy.pal_ref`), the healthy portion (reference / 4) and the kcal spent per step (BMR / 24 x the METy of the running activity, `mety` in `activities.json`, or `energy.mety_idle`). `scripts/health/hunger.gd` grows hunger (kcal) every step with the v1 formula (with d from `scripts/health/sleep_model.gd` and z from `scripts/health/body_size.gd`), says "I'm hungry!" at 0.8 healthy meals after 2 h since the last meal or skip, and eats a meal when it ends, in proportion to the time eaten (Stop = part of a meal). Meals are logged with `kcal_eaten`. A new avatar starts with weight from its z at the WHO median height for the reference age, and ready for breakfast. Simulation is listed before Activities in the autoloads and splits a frame at the end of a day activity, so each step uses the right METy. **Energy, weight and body size (Milestone 10 Task 4):** every step the kcal spent go into a 24-slot energy window (one slot per avatar hour) and take weight off; a meal's kcal go into the window and onto the weight: weight += `body.k` x kcal / `body.kcal_per_kg` (`scripts/health/energy.gd`). The energy deficit penalty U (`GameState.deficit_u`) = 0 below a 30% deficit in the window, 1 at 60%; a new avatar's window starts in balance. `scripts/health/body_size.gd` ages the body by `body.k` x hours (stopping at `body.max_age_months` of the age group), sets height to the WHO median and z (`GameState.weight_z`) from weight / height², and gives the v1 weight score w(z) (`health.weight_score_points`). The starting z is the v1 one (`health.difficulties.<id>.z`). Entertainment has **Screens** (METy 1.3, screen time) and **Football** (METy 7.5, moderate-to-vigorous); `kcal_per_hour` is gone, and the calories-spent record is the energy spent during activities whose intensity is in `energy.record_intensities`. U cuts training gains and targets, the happiness baseline and Physical.

**Training (built in Milestone 10 Task 5, `scripts/health/training.gd`, v1 Step 6).** Fitness and strength (`muscle` is renamed `strength`) are trained **every step**, no longer once per day by the Milestone 4 code. Cardio and Football count as cardio, Strength as strength (`train.cardio_types`, `train.strength_types`). Daily capacity = (60 + 90 x fitness) x (1 - 0.3 x d) minutes per avatar day (reset after any sleep and by the 0-hour rule); minutes beyond it give no effective minutes and build the overreaching load O (`GameState.overreach`: excess minutes per day averaged over 72 h, / 120). Recovery is clock time: cardio tires fully after 120 continuous minutes and recovers with a 6 h time constant; strength tires after 45 minutes and recovers with 24 h (86% after 48 h); a strength session that starts below 60% recovery is too soon: it gives no effective minutes and all its minutes build O (user decision, 25 Oct 2026; v1 predicted strength 0.34 for strength twice a day, and without this rule the model gave 0.75, more than the guideline plan). So is a strength session that starts less than 36 avatar hours after the start of the previous one (Milestone 10.5, team review: `train.strength_min_gap_h`; `GameState.hours_since_strength`; strength every day ends at 0.45 instead of 0.80). Effective minutes = minutes x performance (minigame default score 1, lowered by tiredness from `scripts/health/sleep_model.gd`) x recovery; their average per day over the last `train.average_window_h` avatar hours (24 h: the sum of the last day; `scripts/health/hour_window.gd`, a sliding window shared with the energy window) gives A_cardio and A_strength. Targets: 0.1 + 0.9 x (1 - e^(-2 x minutes / ref)), x (1 - 0.5 x U); fitness and strength move toward them with 30 and 42 body days (k applies); only gains are cut by d, U and O. A new avatar's window holds the minutes that give its starting fitness and strength as targets, so nothing moves before the player acts. Starting fitness and strength come from the v1 difficulty table.

**Sleep (built in Milestone 10 Task 6, `scripts/health/sleep_model.gd`, v1 Step 9).** At each new avatar day (when any sleep ends, or by the 0-hour rule as 0 h) Simulation runs `SleepModel.new_day()`: debt = debt x e^(-(slept / target) x 24 / (5 days x 24 / k)) + max(0, minimum - slept), with the range and target of the age group (child 9 to 12 h, target 10.5; teenager 8 to 10 h, target 9); k applies to the recovery, so a full night repays 86% and no sleep repays nothing; 6 h every night settles at 4.4 h. Sleep measure = (1 - min(1, debt / 8)) x (1 - min(0.3, 0.1 x hours above the maximum)); night quality changes happiness on waking. The starting debt comes from the v1 difficulty table, so Normal starts with 4 h of debt (Sleep 0.5) and is sleepy at once. "I'm tired" (`GameState.tired`) now comes from tiredness = max(d, (hours awake - 15) / 4) >= 0.5, worked out every step; the Clock no longer sets it. While SaveGame loads a save, `Simulation.loading` is true, so the Clock's repeated phase change does not run a new day again.

**Diet and Happiness (built in Milestone 10 Task 7, `scripts/health/diet.gd` and `scripts/health/happiness.gd`, v1 Steps 7 and 10).** `GameState.mental` is renamed `happiness` (UI: "Happiness"). Each meal moves diet quality Q toward x (1 healthy, 0 fast food), craving C and habituation A toward 1 - x, by 1 / (time constant x 4 meals): Q 21 and C 30 real days (body time, divided by k), A 5 avatar days (clock time); a part of a meal moves them by that share. Happiness moves every step toward its baseline (0.15 + 0.30 Physical + 0.25 Sleep + 0.10 Q + 0.20 Fun - 0.2 U - 0.10 screen excess - 0.1 O) with a 12-hour time constant (clock time) and jumps with the v1 events: meals (healthy +0.01 - 0.06 C, fast food +0.01 + 0.06 C (1 - A), using C and A from before the meal), starting cardio or strength (-0.03 (1 - fitness)), exercise within capacity (+0.07 per hour, less when tired) or beyond it (-0.02 per hour), football (+0.10 per hour), screens (+0.05 per hour, only the first 120 minutes of a day), 4 awake hours without screens (-0.02), hungry while awake above 1.2 meals (-0.05 per hour), waking (+0.08 (night quality - 0.5)) and being kept awake at tiredness 1 (-0.02 per hour). Fun and screen excess use a sliding 24-hour window (`mood.fun` types: football, screens, exercise). The starting happiness, Q, C and A come from the v1 difficulty table. **Deleted in Task 7:** the Milestone 4 mood (0 to 100), the habit-change cost (T, alpha, gamma, P_max, H, R), the daily habit scores, `body_test.gd` and the old `calibration_test.gd` (Task 10 writes the new one). `GameState.daily_update()` (when a sleep ends) moves the health bar, and `Habits.day_closed` is emitted. `tests/happiness_test.gd` plays v1 scenarios for 21 days, eating whenever the avatar is hungry: the guideline plan ends at happiness 0.92; with craving 0.9 an abrupt switch to healthy food drops to 0.41 at the lowest (v1 0.40) and a gradual one to 0.44 (v1 0.50).

**Physical, health, failure, risk, XP and the avatar's looks (built in Milestone 10 Task 8).** `scripts/health/health_model.gd`: Physical (v1 Step 8) every step; target health = 1 + 4 x the power mean (p 0.5, equal weights) of Physical, Happiness and Sleep; the displayed health moves 37% of the way to it when a sleep ends; failure timers (target health below 1.3 for 24 h, decision 10; or happiness below 0.10 for 12 h; or the danger state, Milestone 10.5) and placeholder messages by cause (`HealthModel.failure_cause()`: "thinness", "health" or "happiness"). `scripts/health/risk.gd`: risk index R and hidden damage, shown only in the debug panel. `scripts/health/progress.gd`: v1 XP. `scripts/health/avatar_states.gd`: hungry, tired, sad (happiness below 0.3), thin (z below -2), overweight (z above +1), muscular (strength 0.7 or more; with overweight = muscular with fat); the speech bubble says "I'm sad." Since the avatar art (6 Nov 2026, `scripts/avatar/avatar.gd`): the body is obese (z above +2, WHO), overweight (above +1), thin, muscular or healthy, weight winning over muscles (user: muscular with fat shows the overweight body); the face is asleep, tired, sad, happy (happiness 0.6 or more, `avatar_states.happy_from`, placeholder) or neutral; Ill tints the drawing green. Without art the egg is narrower when thin and wider when overweight, has a thicker outline when muscular, heavy eyelids when tired and a frown when sad The physical values box shows calories spent, strength, fitness, weight, height, BMI-for-age z and diet quality. The starting health matches the v1 table for a boy of 10: Easy 3.94, Normal 2.91, Hard 1.95, Very hard 1.49 (1.35 in v1; happiness 0.30, decision 7). **The Milestone 4 health block (`health_m4`), the old XP rules and the `thresholds` group are deleted;** the action-log settings moved to the config group `log`.

**Cardio minigame (Milestone 12, decisions 19 to 30, `MILESTONE_12.md`; sources there).** Cardio only (`"minigame": "cardio"` in `data/activities.json`); football keeps the fixed score (decision 29). `scripts/health/cardio_pace.gd`: capacity = fitness x body x (1 - `capacity_tired_cut` x tiredness), with body = 1 - 0.16 per z above 0, at least 0.4; running cadence from the moderate to the vigorous threshold of the age group (CADENCE-kids: 115 and 130 steps/min for a child, 110 and 125 for a teenager); one tap is one stride (2 steps); run minutes = 10 + 110 x capacity. `scripts/autoload/minigame.gd`: score = 0.5 x rhythm + 0.5 x pace, both averaged over about the last 10 strides, read by `Training.performance()`. **The Breath bar is the fatigue of one session:** it starts at `GameState.cardio_recovery`, falls with avatar minutes / run minutes (faster above the interval), and at 0 the avatar walks (`walk_mety`) until 0.5. With no tap for 3 s the avatar stands still: `Activities.doing_option()` is "" and nothing counts (no activity minutes, no training, idle energy); after 20 s the activity ends (decision 28). The happiness cost of starting exercise comes with the first tap. **A session needs the main screen open (`Minigame.attach()`) and normal speed,** so the scenario tests have no player and keep `minigame.default_score`. `Minigame.changing` makes Simulation run the pending minutes before the avatar changes what it is doing. The session is saved. The concept still says "no separate fatigue system" and "each click is one step": decisions 24 and 25 replace them, and "tired" still means sleepy.

**Strength minigame (Milestone 13, decisions 31 to 38, `MILESTONE_13.md`; sources there).** `"minigame": "strength"` in `data/activities.json`; the same `Minigame` autoload with `kind`, and one `reserve` for the Breath and Muscle bars. `scripts/health/strength_load.gd`: capacity = strength x body x (1 - `capacity_tired_cut` x tiredness), with body = 1 - 0.12 per z above 0, at least 0.4; 8 to 12 repetitions and 1 to 4 sets by capacity (AAP 2020). Down then Up is one repetition; only the expected button works. Score = 0.5 x technique (each press within `on_beat_share` of `press_seconds`, 1 s) + 0.5 x repetitions done of those planned. The Muscle bar starts at `GameState.strength_recovery` and falls per repetition, faster when rushing. A set ends at its repetitions or with the bar empty (never to failure), followed by `rest_seconds` (6 s) of rest, which refills 0.6 of the bar. More sets follow until the chosen time ends (decision 36). Rest counts as session time at the option's METy. Stopping works as in cardio; the rest is not stopping. **The strength start (too soon, the 36-hour gap, the happiness cost) runs at the first press**, so an activity nobody played is not a session. A session that is too soon shows a warning and can still be played (decision 35).

**Football minigame (Milestone 14, decisions 39 to 46, `MILESTONE_14.md`; sources there).** `"minigame": "football"` in `data/activities.json`; decision 29 is replaced. `scripts/health/football_match.gd` is the match: 4 a side seen from above, the avatar's team attacks upwards, computer players, fixed steps and a seeded generator, no screen and no health. `scripts/health/football_load.gd`: the cardio capacity sets speed, the distance at which a team-mate is free and the range of a good shot. Score = 0.5 x timing (a pass to a free team-mate, a shot in range, a tackle in reach) + 0.5 x the share of the last 10 seconds spent moving. Breath falls while moving and with each move, refills when standing still, and at 0 the avatar jogs at `walk_mety`. Goals never change health. The match stops while the avatar waits. Computer players are the same at every difficulty. **Avatar time runs 5 times slower while the avatar plays** (`Minigame.time_share()`, read by the Clock; decision 47), so 60 minutes last about 7 real minutes; energy and training stay per avatar minute. While a team-mate has the ball, Pass asks for it and Shoot makes it shoot; blue computer players never tackle or shoot alone, and Tackle uses the avatar or the nearest blue player in reach (decision 50). A tackle always ends: the loser is pushed back and a computer player stands still for a moment (decision 51). The whole match runs at `match_pace`, 80% (decision 49). Red defends with a presser, a last defender and markers, goes around blue players, runs ahead of the ball, passes only forward and shoots with a clear view; its last defender never counts as blocking a shot. An explanation opens the first time on a device (`Settings.football_help_seen`, `scripts/ui/football_help.gd`; decision 48). Numbers are in the config group `minigame.football`.

**Meal minigame (Milestone 15, decisions 52 to 56, `MILESTONE_15.md`).** Both meals have `"minigame": "meal"`. A fork swings left and right over the avatar, faster with every bite; a tap with the fork at the mouth is a bite, a miss drops the food. A meal is 10 bites; the Tummy bar is green from 6 bites (user, 6 Nov 2026) (`minigame.meal`, placeholders). Done ends the meal, and 10 bites end it by itself. When it ends, `Simulation` takes the result from `Minigame.take_meal_result()`: kcal = bites / 10 x the portion, and `Hunger.eat(food, share, full_share)` lowers hunger as if bites / 6 of the portion was eaten, at most one portion (decision 55). A meal with no bite has no effect. Without a player meals work as before. Space bites and D is Done on a computer.

**Scenario tests (Milestone 10 Task 10; Milestone 10.5 Task 4, `tests/calibration_test.gd`, about 2.5 minutes).** Plays every v1 "Predicted results" scenario through the real game and prints each row at day 21 (and day 60 for five) next to v1, failure (day, cause, z), the danger state, the lowest happiness, the hungry share, meals and kcal a day and strength sessions too soon for every scenario, and PASS or FAIL for every rule of the v1 "Bases fundamental check" (with strength every day added to "too much or too often"), the danger state (the severe diet reaches it and fails before z −5; nothing else reaches it), the variants (girl of 10, teenagers) and the Very hard checks. The player rule is exact: every 30 avatar minutes it looks for "I'm hungry!" and eats at once; it cannot look during an activity; nothing is random. v1's known plans are played (strength twice a day: 40 min cardio, strength 9 and 12 h after waking; 30-minute guideline strength sessions); other plan details are guesses listed for the team (decision 12). **All rules pass with the v1 placeholders.** No value was changed to fit.

**Parity test and the causes of the differences (Milestone 10.5 Task 5, `tests/parity_test.gd`, about 5 minutes).** Extends the scenario test: plays the scenarios with the user's decisions 1, 2 and 7 and the 36-hour gap off and the player eating as soon as the avatar is hungry, then changes one thing at a time and tries the plan guesses. It prints numbers, no pass or fail. Results in `documentation/milestone10_calibration.md`: weight and body size match v1 closely; the severe diet's difference is the scenario (its screens hour blocks a hungry moment); the happiness gap is mostly plan details v1 does not describe (football in the guideline activity, 2 h of screens without sport) plus half-hour meals and the hunger penalty for 4 h of cardio; guideline strength depends on the training window. The training window now averages effective minutes per day over `train.average_window_h` (24 h by default, as before; a week gives 0.76 guideline strength), so the team can choose it.

**Still to define** (see "Por Definir: Sistema de Saúde" and the v1 "Open decisions and risks"): the researched values that replace the v1 placeholders; the team's answers to the proposals in `documentation/milestone10_calibration.md` (plan guesses, training window, eating time and METy, the hunger penalty with fixed portions); diseases (which, how fast; only a risk index exists); the values of the danger state of severe thinness (built in Milestone 10.5 with the review's placeholders); whether active entertainment (football) counts toward the 60 minutes; a European starting point for the measures; XP per day.

## Interface (from the user's sketch)

- Avatar in the centre, standing on a ground line. Short messages from the avatar ("I'm hungry!", "I'm tired", others).
- **Requests (Milestone 16, decisions 57 to 60, `MILESTONE_16.md`).** One at a time, with a small placeholder picture in the bubble, in this order: failure, tired, hungry ("I want fast food!" when craving C is at least 0.5, "I'd like a healthy meal." at 0.15 or less, otherwise "I'm hungry!"), "Can I watch something?" after 3 awake hours without screens, "Can I play football with my friends?" when Fun is below 0.25, then sad, then hello. The player answers by acting. Reactions: "Do I have to?" or "Let's go!" when exercise starts (fitness below or above 0.5), "Yes, fast food!", "Not this again..." and "Just what I wanted!" when a meal starts, and "You never let me watch anything." when four hours without screens count as a refused wish. `scripts/health/requests.gd` only reads the state; the thresholds in the config group `requests` only decide what the bubble shows.
- Top bar (positions and functions from the user's sketch; the art is placeholder):
  - **Top left:** a square **health level** box (the health level, 1 to 5) and, to its right along the top edge, the **health bar** (1 to 5).
  - **Clicking the health level box or the health bar** opens the measures panel directly under the health bar (no gap between them). It shows three bars with their names: **Physical**, **Happiness** and **Sleep amount**. Clicking either again closes it.
  - **Clicking the physical bar** opens a box to the right of the measures panel with the physical **values as numbers, not bars**: calories spent while exercising, strength, fitness (fitness takes the place of endurance), weight, height, BMI-for-age z and diet quality. It closes with the measures panel.
  - **Top middle:** the **XP bar** along the top edge, with "XP current / needed" written on it.
  - **Top right:** a column with, from top to bottom: the **XP level** box, the **24-hour clock**, the **pause** button, the **settings** button and the **Wake** button (a button with the word "Wake" written on it, enabled only after a sleep ends).
- During a minigame a panel takes the place of the four buttons: status, steps, repetitions or goals, the Breath or Muscle bar, the Beat bar, and a large tap button (cardio, Space on a computer), Down and Up (strength, arrow keys), or a joystick with Pass and Shoot or Tackle (football; on a computer no joystick, arrow keys or WASD, Z or J, X, K or Space, P pauses and H helps; the field takes the place of the avatar). The avatar hops or squats with the player and stands still while waiting.
- Bottom: four buttons in a 2x2 grid: **exercise, sleep, eat, entertainment**. Each opens its options. For exercise and entertainment the player first chooses the **minutes on a slider** and then clicks the option (`activity_slider` in config, 5 to 240 minutes, placeholders; Milestone 12). Meals have no slider, because their portions are fixed. Exercise: cardio and muscle strength. Eat: healthy meal and fast-food meal (and Skip meal when hungry); a meal is the feed-the-mouth minigame (Milestone 15). Entertainment: screens and football. Sleep: a **slider** for the hours, up to the longest sleep allowed; when the avatar is not sleepy it says "I'm not sleepy." Full menus for eat and entertainment are decided later. There is **no gardening**.
- **Settings (built in Milestone 11, decision 14):** the settings button opens a panel over the whole screen, at any moment, with the language (Portuguese or English) and "Start a new avatar", which shows a warning and needs a second press. The day pauses while it is open and returns to how it was on Close; sleep keeps running. The language stays with a new avatar. Music and sound settings wait until the music exists.
- While an activity runs: the four buttons are locked, the avatar plays a short repeating animation, a **stop button above the four buttons** ends the activity, and each activity has its own background (user, 7 Nov 2026): `"scenery"` in `data/activities.json`, drawn by `scripts/ui/scenery.gd` with placeholder shapes: **room** (meals: a wall with two windows that show the sky, with stars at night), **outside** (cardio and strength: no building, only the sky and the ground) and **bedroom** (sleep, user, 7 Nov 2026: a bed seen from above on a grey floor that fills the screen; the avatar's picture lies in it, its head on the pillow (the pillow ends just below the chin), and a blanket covers it from the chest down, drawn by a second Scenery node, `Blanket`, in front of the avatar); screens keep their see-through colour and football its field. The ground is grey, from the avatar's feet to the bottom of the screen.
- **Buttons (user, 7 Nov 2026):** rounded with a border; white with black text and border in the day (`scenes/ui/main_theme.tres`, every screen) and black with white text and border at night (`scenes/ui/night_theme.tres`, put on the main screen while the sky is more night than day, `daylight` in config, the same hours as the sky).
- **Bars (user, 7 Nov 2026):** every bar has the same rounded shape and border as the buttons (black by day, white at night) and a dark empty part; the fill is green for health (red in the danger state, the type variation `HealthBarDanger`), white for XP and grey for Physical, Happiness, Sleep and the minigame bar. The buttons around the health and physical bars are flat (they only catch the click). The texts on the bars have a black outline. **The XP level box** (user, 7 Nov 2026) looks like the health level box: 88 x 88, rounded, white with black text by day and black with white text at night (theme variations `LevelBox` and `LevelLabel`), "Lv" above the number. ## Quality checks

- After changes, run the project headless to catch script errors, and run the tests in `tests/` (each prints PASS or FAIL and ALL PASSED at the end; `calibration_test.gd` takes about 2.5 minutes and `parity_test.gd` about 5, so give them a longer time limit). A test that hits a script error never quits, so run tests with a time limit, for example `perl -e 'alarm 300; exec @ARGV' "/Applications/Godot 2.app/Contents/MacOS/Godot" --headless --path . -s res://tests/save_test.gd`. On this Mac Godot is installed as `Godot 2.app`, so the binary is `"/Applications/Godot 2.app/Contents/MacOS/Godot"`, for example `"/Applications/Godot 2.app/Contents/MacOS/Godot" --headless --path . --quit`.
- In the Godot editor, close the game window instead of pressing Stop ■, because Stop kills the game without the save on close. If it is not available, tell the user which scene to open and what to look for.
- No hard-coded game numbers in scripts. No use of the device clock for game time.
- Web build: `"/Applications/Godot 2.app/Contents/MacOS/Godot" --headless --path . --export-release "Web" docs/index.html`; check it with the `web-build` server in `.claude/launch.json` (port 8060). In the browser, Godot reads single key presses, not pasted text.
- Keep commits small, with clear messages.
